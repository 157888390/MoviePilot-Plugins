# 反吸血守卫（PeerGuard）· V3

轮询 qBittorrent 的 peer 列表，按 **PeerID**、**客户端名**、**行为特征** 识别吸血客户端，
命中后调用 qb 的 `transfer/banPeers` 让对方断开。定位是 [PeerBanHelper](https://github.com/PBH-BTN/PeerBanHelper)
的裁剪版：不要 JVM、不要额外容器，直接跑在 MoviePilot 进程里。

## 与 PeerBanHelper 的取舍

| 能力 | 本插件 | 说明 |
| --- | --- | --- |
| PeerID 黑名单 | ✅ | 读 qb 的 `peer_id_client` 字段（qb 4.5+ 提供），迅雷等主要靠这条 |
| 客户端名黑名单 | ✅ | 正则匹配，PeerID 缺失时的兜底 |
| 虚假进度检测 | ✅ | 进度回退，或"下载量涨了进度不动" |
| 超量下载检测 | ✅ | 单 peer 累计下载超过种子体积 N 倍 |
| 纯吸血检测 | ✅（默认关） | 连续多轮有下载零上传；PT 下载期本就零上传，容易误伤 |
| 内网 / CIDR 白名单 | ✅ | 内网与回环恒定放行 |
| **BTN 云端规则** | ✅（默认关） | 填 PBH 的 AppID / AppSecret 即可拉云端 IP 黑名单、允许名单与 PeerID / 客户端名规则 |
| GeoIP / 国家 / ASN 封禁 | ❌ | 需要 mmdb 库，塞进插件会把体积和内存拉上去（BTN 的 GeoIP 结论已体现在云端 IP 黑名单里） |
| PT 站点联动 / 表达式引擎 | ❌ | 需要逐站点适配与表达式解释器，实现成本高，收益不抵 |

**一句话选型**：只想挡住迅雷这类明显吸血端、又不想多养一个 Java 服务 → 用本插件；
需要站点联动、自定义表达式 → 用 PeerBanHelper。

## 前置条件

1. **qBittorrent 4.5 或更高**。低于此版本没有 `peer_id_client` 字段，PeerID 规则会全部失效，
   只剩客户端名规则。
2. **下载器必须能拿到 peer 的真实 IP**。qb 跑在 Docker 里时用 `host` 网络；
   桥接模式下所有 peer 的来源 IP 都会变成容器网关，封禁会**误封整个内网**——
   插件虽然会把内网地址放行（表现为"规则不生效"），但根因是网络模式。
3. 已在 MoviePilot 的「下载器」里配好一个 qbittorrent 类型的下载器。

## 配置项

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 启用插件 | 关 | 关闭后不再注册轮询服务 |
| 下载器 | 首个 qb | 只列出 qbittorrent 类型的下载器 |
| 轮询间隔（秒） | 30 | 下限 10 秒；每轮只拉"活跃种子"的 peer 列表 |
| 演练模式 | **开** | 只记录命中项、不真封禁。建议先跑几天看误判 |
| 单轮封禁上限 | 20 | 规则写错时的保险丝 |
| 检测虚假进度 | 开 | 命中原因记作 `progress_regress` / `progress_fake` |
| 检测超量下载 | 开 | 命中原因记作 `excessive` |
| 检测纯吸血 | 关 | 命中原因记作 `leech_only` |
| 超量倍数 | 1.5 | 累计下载 > 种子体积 × 该倍数判定超量 |
| 进度停滞阈值（MB） | 50 | 下载了这么多字节而进度几乎没动，判为假进度 |
| PeerID 前缀黑名单 | 内置 12 条 | 每行一条，忽略大小写；对照 PBH 默认规则集裁剪 |
| 客户端名正则 | 内置 8 条 | 每行一条，非法正则会被跳过 |
| IP 白名单 | 空 | 每行一个 CIDR，内网不需要填（恒定放行） |
| 封禁时推送 | 关 | 每轮有新增封禁时发一条汇总通知 |
| 启用 BTN 云端规则 | 关 | 见下节；凭证齐全才生效 |
| 云端 IP 黑名单 | 开 | 命中即封，原因码 `btn_ip` |
| 云端 PeerID / 客户端名规则 | 开 | 原因码 `btn_peer_id` / `btn_client` |
| 云端刷新间隔（秒） | 600 | 下限 60；规则未变更时服务端回 204，几乎零开销 |
| 回传封禁记录 | 关 | 需你显式同意，见下节 |

## BTN 云端规则（可选）

BTN（BitTorrent Threat Network）是 PBH 背后的公共威胁库。本插件按
[BTN-Spec 2.0.1](https://github.com/PBH-BTN/BTN-Spec) 实现了读取侧：

1. 在 PBH 用户面板里创建应用，拿到 **AppID / AppSecret**（一对应用一个）。
2. 在插件设置里打开「启用 BTN 云端规则」，填入两个值。
3. 首次启用会立刻在后台拉一次，之后每 `云端刷新间隔` 增量刷新。

拉到的四类数据：

| 能力 | 用途 | 落点 |
| --- | --- | --- |
| `ruleIpDenylist` | 云端 IP / CIDR 黑名单（实测 1200+ 段，合并后） | 直接封，优先于所有本地规则 |
| `ruleIpAllowlist` | 盒子 / 公益站点登记表 | 命中即放行，优先于云端黑名单 |
| `rulePeerIdentity` → `peer_id` | 云端 PeerID 规则 | 与本地 PeerID 前缀并列，命中记 `btn_peer_id` |
| `rulePeerIdentity` → `client_name` | 云端客户端名规则 | 与本地客户端名正则并列，命中记 `btn_client` |

判定顺序：内网 → 本地白名单 → 云端允许名单 → **云端黑名单** → 本地/云端 PeerID
→ 本地/云端客户端名 → 行为规则。云端名单改动不影响行为规则的"连续 N 轮"计数。

细节：

- 缓存存在插件数据目录（`/config/plugins/PeerGuard/btn_*.txt|json`），**离线可用**：
  插件重启先用缓存装配引擎，再慢慢刷新。删缓存等于下次全量重下。
- 刷新失败（网络/鉴权）只写进详情页的状态行，本地规则继续工作，不会连带停摆。
- `rule_peer_identity` 里的 `ip` / `port` / `script` 段本插件不处理：前者已由
  `ip_denylist` 覆盖，后两者需要 PBH 的表达式引擎。
- **回传封禁（`submit_bans`）默认关闭**。按规范，提交任何数据前必须取得用户同意；
  开启后只上报 `peer_ip / peer_port / peer_id / 客户端名 / 命中原因`，
  种子只给不可逆识别码（`sha256(info_hash + crc32_le(info_hash))`，见规范算法），
  不上报种子名称或内容。提交失败直接丢弃、不重试（同为规范要求）。

## 接在哪儿

    每 N 秒                               命中则
    ┌──────────┐  torrents/info  ┌────────────┐  transfer/banPeers  ┌────┐
    │ 调度服务  │ ──────────────> │ RuleEngine │ ──────────────────> │ qb │
    └──────────┘ sync/torrentPeers└────────────┘   （会话级封禁）     └────┘

"活跃种子"按 qb 的口径筛：有 leech，或者有上传/下载流量。`stalledUP` 且无人连接的种子直接跳过，
所以 5000 个保种种子的场景下一轮也只有几个种子需要真正拉 peer。

## 接口

全部 `auth: "bear"`，路径前缀 `/api/v1/plugin/PeerGuard`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/overview` | 运行状态、累计统计、最近错误 |
| GET | `/banlist?limit=50` | 封禁记录（倒序） |
| POST | `/check` | 立即检查一轮并返回命中明细，**不封禁** |
| POST | `/ban` | 手动封禁，body `{"peers": ["1.2.3.4:6881"]}` |
| POST | `/clear` | 清空插件内的封禁记录（不影响 qb） |
| GET | `/btn` | BTN 状态：名单条数、规则版本、上次刷新时间 |
| POST | `/btn/refresh` | 立即全量刷新云端规则（换 AppID 或规则明显不对时用） |

`/check` 是调规则最顺手的入口：改完规则先打一次，看返回的 `items[].detail` 是不是你想封的人，
再关掉演练模式。

## 两个必须知道的限制

1. **封禁是会话级的。** qb 的 `banPeers` 没有对应的解封接口，封禁在 qb 重启后清空。
   因此本插件也不提供"自动解封"——所谓封禁时长在这里不成立，记录只用于查看。
2. **不开 BTN 就得自己养规则。** 默认名单是某一时刻的快照；吸血客户端会换 PeerID 前缀与
   客户端名，本地规则跟不上。想省事就填 AppID / AppSecret 走云端规则，只需在遇到云端也
   漏掉的变种时补本地规则。

## 误判怎么排查

- 先在演练模式看 `/banlist`，`detail` 字段写清了命中哪条规则、当时的数值。
- 误伤正常客户端时，把对方的 PeerID 前缀或客户端名加进白名单式的排除——目前没做"排除名单"，
  最省事的做法是把对应规则收紧（比如把 `^QQ` 改成 `^QQ旋风`）。
- 内网 peer 被误封，先检查 qb 是不是桥接网络（见"前置条件 2"）。
